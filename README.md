# Space Mission Design Game｜架構與流程草案

## 原型啟動

使用 Node.js 24 LTS（或 22.12 以上的 22.x）和 npm。

```sh
npm ci
npm run dev
```

在瀏覽器開啟 Vite 顯示的網址，預設為 `http://localhost:5173`。單人模式可直接玩。選 EN 或繁中可切換文案。同一瀏覽器、同一網址會保留一個單人自動存檔，刷新後在大廳選「繼續任務」。開始新局會覆蓋該存檔。

### 單人試玩

立方衛星有 6 個遊戲週和 `$1,000,000` 的遊戲預算，首次試玩目標為 3–5 分鐘。從大廳查看簡報，再開始任務。操作頁依序顯示當前選擇。實驗室可點各部門查看近況，或快轉組裝與整合演出。功耗明細、測試證據和決策紀錄可展開查閱。

| 路徑 | 操作 | 預期結果 |
| --- | --- | --- |
| 穩健通關 | 保留基本成像儀、基本供電、同時操作與標準發訊。依序完成可行性評估、定版、製造、整合及飛行審查。首次通聯選必要觀測，逐批交付研究單位。 | 第 4 週通過審查，地面收到 2 批可用資料。 |
| 退回後補救 | 選高解析成像儀並保留基本供電及同時操作。完成整合，電力組會保留超限讀值並提出修正。執行「錯開操作排程」，重測後送審。通聯選全部可用觀測，逐批交付。 | 第 4 週看到 13 W 需求、10 W 供應。修正花 1 週和 `$60,000`，重測花 1 週和 `$80,000`。第 6 週可通過審查，地面收到 3 批。 |
| 到期未發射 | 保留基本酬載及供電，選提早發訊設定。完成整合，等通訊組回報退回原因後，展開「其他操作」讓時間經過兩週。 | 首次發訊為 T+20 分鐘，低於本局要求的 30 分鐘。第 6 週以未發射結算。 |

定版前可花 1 週和 `$50,000`分析功耗與操作時序。以高解析成像儀搭配基本供電做分析，然後在定版前改成錯開操作，可在第 5 週通過審查。高解析成像儀搭配加強供電和標準發訊時，首次通聯傳回全部資料可達成額外目標。基本成像儀若把通聯容量留給飛行診斷，地面登錄診斷後會以已發射、交付未達標結算。

整合報告顯示模擬分離、展開裝置與首次發訊的時間戳。FRR 使用首次發訊時間減去分離時間，並與本局搭載介面要求比較。30 分鐘是遊戲設定。結算分別顯示設計預估、驗證證據、地面實收資料和決策紀錄。 [NASA《CubeSat 101》§6.9.1](https://science.nasa.gov/wp-content/uploads/2023/06/nasa_csli_cubesat_101_508.pdf#page=68)

### 多人本機試玩

準備 JDK 21 以上，先在一個終端機啟動 Auth 和 Firestore 模擬器，再在另一個終端機開發伺服器。首次執行會下載 Firestore 模擬器。

```sh
npm run emulators
```

```sh
VITE_FIREBASE_EMULATORS=true npm run dev
```

1. 用兩個獨立瀏覽器設定檔開啟同一個 Vite 網址。一般視窗和一個無痕視窗也可以。
2. 第一個視窗選「多人審查」並以 PM 身分建房。第二個視窗輸入八碼房間碼，選科學、電力或通訊組。
3. 隊友送出一項提案後，可換方案再送一次。PM 畫面會同步提案。未送提案的部門會有遊戲代提，至少一位隊友送出提案後才可確認。
4. PM 選一個提案並確認重測。各視窗都會收到相同判定，可各自切換語言。直接刷新會用原匿名身分回到房間。角色依瀏覽器設定檔保存，回大廳後可用原房間碼返回。

這個原型每房一場整合審查。房間碼是邀請憑證。Firestore 禁止列舉房間，允許持碼匿名玩家讀取該房間。角色認領、提案和 PM 確認由 [Firestore 規則](firestore.rules)約束。確認交易使用回合 ID，寫入一次已選部門與方案 ID，之後各裝置用共用規則計算相同的整合證據與資源支出。

### 驗證與部署

```sh
npm run typecheck
npm run build
npm test
npx playwright install chromium
npm run test:browser -- tests/single.spec.ts
npm run test:team
```

`test:team` 會自動啟停模擬器。執行前先關閉手動啟動的模擬器，釋出 8080 和 9099。測試使用獨立 Chromium 瀏覽器身分，涵蓋 2 人與 4 人房、提案同步及修訂、Firestore 寫入權限、並發確認和刷新恢復。

部署單人版時，把 `npm run build` 產生的 `dist/` 放到靜態主機。部署多人版時，使用團隊自己的 Firebase Spark 專案。新增 Web App，啟用 Authentication 的 Anonymous 登入，建立 Cloud Firestore 資料庫，將 [`.env.example`](.env.example) 複製為 `.env.local`，填入 Web App 的公開設定並保留 `VITE_FIREBASE_EMULATORS=false`。使用 Firebase Hosting 可執行下列指令。

```sh
npm run build
npm exec -- firebase login
npm exec -- firebase deploy --only firestore:rules,hosting --project YOUR_PROJECT_ID
```

部署後用兩台裝置各選一個角色，重跑建房到結算。雲端驗收需要專案存取權、啟用的匿名登入和 Firestore，及可連線的站點。 [Firebase 匿名登入](https://firebase.google.com/docs/auth/web/anonymous-auth) · [Firebase Hosting](https://firebase.google.com/docs/hosting/quickstart)

### 故事與文案交接

- 故事架構、任務分支和正式任務文案草稿放在 [`docs/story/`](docs/story/)。
- 在 [繁中](src/i18n/zh-TW.ts)與[英文](src/i18n/en.ts)字典更新 `briefStory`、`briefDialogue`、各角色的 `*Brief`、階段說明和結局文案。保留 `{count}` 等變數供遊戲填入數值。
- 在 [`src/missions/cubesat.ts`](src/missions/cubesat.ts) 調整初始配置、選項、成本、門檻和部門提案。變更多人提案 ID 或代提方案時，也需更新 [`firestore.rules`](firestore.rules) 並重跑 `npm run test:team`。
- 大廳會顯示團隊聲望與後續任務進度。入軌火箭和登月仍在規劃中。原型的實際操作範圍是立方衛星單人任務和多人整合審查。

### 新增任務

遊戲規則在 [`src/game/mission.ts`](src/game/mission.ts)，各任務共用。新增一個任務的步驟：

1. 在 `src/missions/` 新增規則檔，匯出符合 [`MissionRules`](src/game/types.ts) 的物件。內容包括選項組 `groups`、各項工作的成本 `costs`、整合測試判定 `test`、補救方式 `remedies`、任務模擬 `fly`、結局文案 `outcomes`、聲望 `reputation`，以及可選的固定觸發事件 `events`。可以參考 [`cubesat.ts`](src/missions/cubesat.ts)。
2. 在 [`src/missions/rules.ts`](src/missions/rules.ts) 的 `missionRules` 登記，`missionCatalog` 的順序就是解鎖順序。
3. 新增對應的畫面元件（參考 [`cubesat-ui.tsx`](src/missions/cubesat-ui.tsx)），在 [`src/missions/index.ts`](src/missions/index.ts) 的 `missions` 登記。
4. 文案加進兩份 i18n 字典。

達成前一個任務的最低要求後，下一個任務才會解鎖。進度和聲望存在瀏覽器（`space-mission.progress.v1`）。事件觸發時，玩家要先做選擇才能繼續。選擇結果記在 `game.events`，規則可以用 `eventChoice` 讀取。任務 `records` 回傳的成果會帶進之後的任務（`game.records`），可以用來觸發邀約。

[官方挑戰資源](https://www.spaceappschallenge.org/2026/challenges/space-mission-design-game/?tab=resources)列出《CubeSat 101》。大廳使用立方衛星的像素插畫。

## 架構選型

採用 **React + TypeScript + Vite**，以 npm 管理套件，做成可靜態部署的網頁遊戲。第一版的任務內容隨程式打包，單人存檔可用瀏覽器的 `localStorage`。多人連線方案見[多人合作草案](docs/multiplayer.md)。 [Vite 靜態部署](https://vite.dev/guide/static-deploy.html)

| 模組 | 負責內容 |
| --- | --- |
| 畫面 | 顯示目前階段、資源、組別回報與可用操作，把玩家動作送給規則。 |
| 遊戲規則 | 用純 TypeScript 函式更新單局狀態，由 React 的 `useReducer` 接到畫面。規則執行工作、扣資源、檢查需求和審查條件，並記錄判定原因。隨機事件的抽選結果當作輸入保存，方便重現同一局。 |
| 情境資料 | 每個任務一份具型別的 TypeScript 資料。任務定義初始工期、預算與需求。選項定義文案鍵、可用階段、前置條件及資源或設計的變動。事件定義何時可出現、發生時改變什麼。各任務共用判定方式。 |

畫面從同一套規則取得「還能做什麼」「為什麼這項不通過」和實際結算。回報使用固定文字模板，填入規則算出的需求名稱、門檻和結果。**可以用 LLM 在開發時草擬選項、事件文案和邊界案例**，由隊員確認工程因果和數值後提交。玩家遊玩時的選項、判定與回報都由瀏覽器執行。 [React useReducer](https://react.dev/reference/react/useReducer)

### 雙語

遊戲支援**繁體中文（`zh-TW`）與英文（`en`）**。大廳和任務中都可切換。首次依瀏覽器偏好選擇，兩種語言皆未匹配時採英文。手動選擇記在本機，切換時沿用當前進度。

介面、任務簡報、選項、事件、審查回報與結算共用文案鍵，分別查兩份具型別的 TypeScript 字典。遊戲規則和存檔使用固定識別碼、判定原因與數值，切換語言時由畫面重新套用文案。新增玩家看得到的內容時，在同一份 PR 補齊中英文。

### 選項怎麼組合

用共用狀態串起選項的後果。以立方衛星為例，酬載方案改變耗電，供電方案改變可用功率。兩組各有兩種選項，就能搭出四種配置。整合測試用同一條規則比較同時運作時的電力需求和供電上限，回報哪一項需求通過、哪一項有缺口。重測取得新證據，換供電方案或調整操作排程會改變實際結果。

## 使用者流程

**大廳 → 選擇任務 → 技術選型與可行性 → 詳細設計與定版 → 製造與子系統驗證 → 整合測試與發射審查 → 任務模擬 → 結算**

### 大廳與任務簡報

大廳選「開始新局」後，玩家從已解鎖的任務卡選一張。卡片顯示難度與預計遊玩時間，未解鎖的卡片顯示解鎖條件。任務簡報顯示目標、最低要求、額外目標、初始預算與交付期限。玩家確認後進入任務工作台。

完整流程跑通後，可加一個瀏覽器自動存檔。每次確認決策或解決事件後存下整局狀態，包含所選任務和已發生的事件。大廳有存檔時顯示「繼續任務」。跨局保留團隊聲望、解鎖進度及會觸發後續邀約的任務成果。

### 工作台與回合

工作台常駐顯示目前階段與三個取捨指標。

- **時間**顯示剩餘週數和交付期限。
- **經費**顯示剩餘可用額與目前方案的預估剩餘支出。
- **任務完成度**逐項顯示需求預估能否達標、是否已有驗證證據，以及任務操作後的實際成果。規劃時讓玩家看得出哪些最低要求還有缺口。

每回合代表 1 週，玩家從各組提案選一項主工作，例如分析、製造、測試或返工。比較方案時顯示時間、經費與受影響的需求，按「執行並推進一週」後結算。閱讀簡報、比較選項和送審可以隨時做。退回時顯示待補項目，補分析、重做或重測才消耗工期。

各任務有自己的交付期限，工期可跨階段挪用。下表的開發週數是遊戲內工期，遊玩時間則是從選任務到結算的首次試玩目標。

### 各階段怎麼玩

| 階段 | 玩家操作與離開條件 |
| --- | --- |
| 技術選型與可行性 | 先從組別提案選任務架構，確認各組負責哪些需求（MDR）。接著選要優先做的分析或原型測試。關鍵可行性門檻達標，其他已知風險有處理方案，就能通過初步設計審查（PDR）。 |
| 詳細設計與定版 | 確認元件、跨組介面與驗證方式。關鍵設計審查（CDR）通過後定版，才開始製造。之後變更要列出受影響的介面與驗證項目，支付返工成本並重測相關項目。 |
| 製造與子系統驗證 | 選哪一組先開工、哪一項先驗證。追蹤各組交件與測試結果。必要的子系統就緒後，就能進整合。 |
| 整合測試與發射審查 | 跑跨組測試，檢查整套系統能否完成操作。發現問題可根據報告調整設計或操作方式，再重測。必要條件有證據支持後，才能通過飛行準備審查（FRR）並進入任務模擬。 |

審查名稱與目的參考 NASA，工期和通過門檻是遊戲原型設定。 [NASA 審查準則](https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_7123_001D_&page_name=AppendixG)

### 難度與遊玩節奏

「極限方案」指能把某項任務表現往上推，但要多投入工期、經費或驗證工作的選項。各難度以可行的方案組合來調整。

| 任務 | 初始期限 | 首次遊玩目標 | 玩家會遇到的取捨 |
| --- | ---: | ---: | --- |
| 簡單／立方衛星 | 6 週 | 3–5 分鐘 | 四個開發階段各安排一項主工作，審查結論直接出現在工作台。全選穩健方案就能達標，留兩週給補測、修正或挑戰額外目標。 |
| 中等／入軌火箭 | 12 週 | 8–12 分鐘 | 以一項極限方案搭配其餘穩健方案作為平衡基準。開局的預算可能容許兩項，若遇到經費削減，工作台會更新剩餘預算與預估支出，讓玩家比較該保留哪一項。 |
| 困難／登月計畫 | 20 週 | 15–25 分鐘 | 數項關鍵需求需要極限方案。玩家得在設計階段選擇自己研發或提前談合作，整合階段再用手上的資金、技術支援和工期應對問題。政府要求提前交付時，重新安排優先順序，保住最低需求。 |

登月計畫要有至少兩條可通關的路線供試玩，例如用預付款支應自主研發，或用合作方的技術支援縮短關鍵工作。合作方式要能影響後面的整合選項，每次主要危機都讓玩家選擇要用什麼資源解決。通過飛行準備審查後，模擬分成發射、月球轉移、登月三段，讓玩家看到前面保下來的能力各在哪一段派上用場。

**合作研發**會占用一個或多個主工作回合，這段時間主線少做相應的工作。合約在接受前列明所需週數、回報與取得時點。預付款能先補經費，里程碑款要等合作交件，技術支援則可縮短指定的研發或驗證工作。玩家依當前缺口判斷接案能否趕在主線需要前帶來幫助。

### 突發事件與測試結果

- **外部事件**可以在回合結束時抽到。經費削減影響後續能花的錢，供應延誤推遲交件，交期提前會減少剩餘回合。經費和交期事件安排在玩家還有時間調整時出現。事件畫面列出變動前後的剩餘資源，再讓玩家回工作台改方案、重排工作或放棄額外目標。
- **工程問題**接到玩家的設計選擇。原型可先用明確門檻判定，讓同一設計在相同條件下重測得到同樣結果。例如為了省錢選低餘裕方案，子系統單獨測試都能過，整合時兩個組別同時運作卻超過電力上限。玩家可以增加供電或調整操作排程，重測後看問題是否解決。若之後要加入故障機率，再讓前期選型與風險處理影響各類故障的機率。

### 任務模擬與結算

通過飛行準備審查後，以任務模擬判定成果。立方衛星用一次簡短操作收尾，較長的任務可拆成數個關鍵操作。期限當週的工作完成後仍可送審。若審查未通過且工期已用完，或預算不足以繼續必要工作，玩家進入「未發射」結算。

- **花了多少**：原始與調整後預算與期限、實際支出、使用週數。
- **做到哪裡**：最後通過的審查、已完成與未完成的工作、是否發射。
- **達成什麼**：逐項顯示需求門檻、驗證證據、任務中的實際成果。未進入任務模擬的項目標為「尚無任務結果」。列出一兩個影響最大的決策，並提供「重玩同一任務」和「回大廳選任務」。

## 原型驗收與待討論

1. **立方衛星先可玩。** 先做酬載、供電兩個決策點，各提供穩健與高性能方案，再加一個能補救的整合問題。驗收正常完成、退回後補救、到期未發射三條路徑。確認結算能指出是哪個選擇造成缺口。兩種語言各從大廳玩到結算一次，另確認任務中切換後的進度、動態回報與版面。
2. **入軌火箭沿用流程。** 換任務需求與選項，先加一張固定觸發的砍預算事件，驗證兩項高性能方案如何縮到一項。固定情境跑通後再加入隨機觸發。
3. **登月計畫擴充合作。** 先做兩條合作路線與一個交期提前事件，確認兩條路都能滿足最低需求。記錄各任務的首次結算用時。

團隊再決定各任務的具體交付成果、組別、正式審查節點、選項成本、驗證門檻，以及事件與合作案的數值。

## 雙機協作

兩台機器以同一個 GitHub repo 的 `main` 為基準。賽前先確認兩邊能登入 GitHub、讀取 repo，並裝好同一個 Node.js LTS 主版本與 npm。全球籌辦團隊說明，正式製作從所屬場次開賽後開始。 [2026 Space Apps 籌辦團隊答覆](https://github.com/nasa/spaceapps/discussions/1827)

開賽後由一台先建 React + TypeScript + Vite 骨架，提交 lockfile，驗證 `npm run dev` 和 `npm run build`，再推到 `main`。兩台拉到同一版後用 `npm ci` 安裝。

| 分工 | 分支與主要目錄 | 第一個可交付成果 |
| --- | --- | --- |
| 機器 A／畫面 | `codex/game-ui` · `src/ui/` | 做大廳、工作台和結算，先用假資料把畫面串起來。 |
| 機器 B／遊戲規則與內容 | `codex/game-rules` · `src/game/`、`src/missions/` | 先做立方衛星，能開局、執行工作扣資源、送審並結算。 |

開分支前，兩人先約定畫面要讀的欄位與可送出的動作。畫面讀取目前階段、剩餘週數、經費、需求狀態和可用行動。遊戲規則接收開始任務、執行工作、送審等動作，回傳更新後的狀態。新增欄位時在 PR 附一筆範例，方便另一台更新假資料或接線。

各自從最新 `main` 開分支，完成一段能跑的改動就推分支開 PR。先合併立方衛星的畫面與規則，跑一遍大廳到結算。入軌火箭、登月計畫與存檔再各自接到這條流程。
