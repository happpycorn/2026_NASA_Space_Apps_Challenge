# 多人合作草案

第一個多人情境是立方衛星的一場整合審查。每位玩家負責一個角色，拿到該部門的資訊與提案選項。兩到四人都保留一位 PM，由遊戲提供空缺部門的提案。單人局同樣使用這組提案和整合判定。

| 角色 | 手上的資訊與要交的提案 |
| --- | --- |
| 科學組 | 看最低交付要求和額外觀測的價值，排觀測順序，提出哪些觀測可挪動或割捨。 |
| 電力組 | 看各操作的耗電和供電上限，指出哪些操作無法同時進行，提出錯開操作或加強供電的方案。 |
| 通訊組 | 看地面站可用時段與下傳容量，安排何時下傳、優先傳哪些資料。 |
| PM | 看共同的工期、經費與任務要求，整合三組提案，決定要花資源改設計、改排程，或放棄額外目標，再送審。 |

## 第一場試玩

1. 科學組希望用一個時段做額外觀測，通訊組也要用同一時段下傳。電力組發現同時運作會超出供電上限。
2. 各組提出方案，PM 看完請各組針對衝突修改一次提案，再確認一套方案。
3. 遊戲判定整合測試結果，顯示工期與經費變化、預估可下傳的資料，以及差在哪一項限制。

先用共用畫面或紙筆試玩，觀察有沒有玩家因為另一組提供的資訊而改方案。這場整合審查用於驗證合作玩法，完整的立方衛星局仍以大廳到結算為首要交付。

## 連線原型

若做成每人一台裝置，先用 Firebase 免費 Spark 方案。Firebase Hosting 放靜態網頁，匿名登入識別房間成員，Cloud Firestore 即時同步提案、回合和結果。 [Firebase 方案](https://firebase.google.com/pricing/) · [匿名登入](https://firebase.google.com/docs/auth/web/anonymous-auth) · [Firestore 即時監聽](https://firebase.google.com/docs/firestore/query-data/listen)

流程保留「建立或輸入房間碼 → 選角色 → 各組送建議 → PM 拍板 → 全員看到結果」。房間保存目前回合和已確認結果。同一瀏覽器刷新後，依原本的登入身分恢復角色與回合。

組員只能寫自己的提案，只有 PM 可以確認回合。用 Firestore 安全規則限制操作，確認時用交易檢查回合是否已結算。兩台裝置先走完一次流程，再驗證組員無法結算、PM 重複按只結算一次、刷新可回到當前回合。 [Firestore 安全規則](https://firebase.google.com/docs/firestore/security/get-started) · [Firestore 交易](https://firebase.google.com/docs/firestore/manage-data/transactions)
