# 中等／入軌火箭

團隊接到入軌示範合約。最低要求是把無人測試酬載送入指定軌道，並交付足以確認示範結果的資料。團隊還希望提高承載餘裕，或多帶回一組飛行診斷資料。

資料檔是 [`src/missions/orbital-launch.ts`](../../src/missions/orbital-launch.ts)，文案鍵都以 `orbital` 開頭。本章尚未接上規則引擎。[`tests/orbital-launch.test.ts`](../../tests/orbital-launch.test.ts) 依本文件的規則重跑每條驗算路線。

文中的質量、經費、週數和門檻都是**遊戲設定**。工程因果對照 NASA 來源，連結附在各節。

## 任務與資源

| 項目 | 數值（遊戲設定） |
| --- | --- |
| 初始期限 | 12 週。期限當週的工作完成後仍可送 FRR。 |
| 合約總額 | 196，分兩期。第 2 週結束時第二期減 20，剩 176。 |
| 最低要求 | 70 kg 測試酬載進入指定軌道，地面收到 2 單位軌道確認資料。 |
| 額外目標 | 以試車數據證明 20 kg 承載餘裕，或地面收到 3 單位飛行診斷資料。達成一項即可。 |
| 首次遊玩目標 | 8–12 分鐘。 |

這一章的主題是**分析值和測試值的差別**。火箭的運載能力一開始只有分析值，熱試車後才有實測值。NASA 系統工程手冊列出四種驗證方法：分析、檢查、展示、測試。沒有原型或整合產品時通常用分析，測試則是用實體產品取得詳細數據。 [NASA 系統工程手冊 §5.3](https://www.nasa.gov/reference/5-3-product-verification/)

組別有三個：推進與結構組、航電與遙測組、地面與靶場組。發射段是 NASA 簡報四個任務區段之一。 [Design and Develop Science Missions 第 8 頁](https://www.nasa.gov/wp-content/uploads/2025/04/250323-design-and-develop-science-mission.pdf#page=8)

| --- | --- | --- |

| 第 2 週結束，出資方削減第二期經費 | 留承載餘裕、留額外診斷、兩項都退回基本方案，或刪掉測試只靠分析值飛行。 | 總經費 196 → 176。這時還沒定版，換選項不花工期。 |

第一版的砍預算事件固定在第 2 週觸發。定版最早在第 3 週，所以玩家一定是先看到新預算才採購硬體。之後改成隨機觸發時，「預算未被削減」就是沒抽到事件的那一支。

### 運載性能

- 承載質量 ＝ 測試酬載 70 kg ＋ 遙測 ＋ 適配器。
- 餘裕 ＝ 上面級運載能力 − 承載質量。
- 沒做熱試車時，審查和工作台顯示分析值。做過熱試車後改用試車值。
- 飛行時一律以試車值判定。餘裕小於 0 就進不了指定軌道。

火箭的空重是酬載加結構。結構越輕，同樣的推進劑能送上去的酬載越多。 [NASA Glenn：Mass Ratios](https://www1.grc.nasa.gov/beginners-guide-to-aeronautics/mass-ratios/) 火箭要有額外的性能餘裕、要去你要的軌道，才載得了你的酬載。 [CubeSat 101 §1.3](https://science.nasa.gov/wp-content/uploads/2023/06/nasa_csli_cubesat_101_508.pdf#page=17) 質量超出發射方分析範圍會被撤下。 [CubeSat 101 §6.4](https://science.nasa.gov/wp-content/uploads/2023/06/nasa_csli_cubesat_101_508.pdf#page=65)

SLS 芯級在首飛前做了完整時長的熱試車，四具引擎點火約八分鐘，工程師用這批數據判斷芯級能否出廠。 [NASA Green Run 更新](https://www.nasa.gov/blogs/missions/2021/03/18/green-run-update-full-duration-hot-fire-successfully-completed-on-mar-18/) 軌道與發射窗口分析可用 NASA 的 GMAT。本章的運載能力是遊戲設定，沒有用 GMAT 算過。 [GMAT](https://software.nasa.gov/software/GSC-19468-1)

### 資料與通聯

- 軌道確認資料 2 單位。飛行診斷資料 3 單位。
- 第一次地面通聯的容量由地面站方案和有無演練決定。
- 玩家在通聯時選先傳哪一種。先傳的傳完，剩下的容量才給另一種。

飛行數據是校正火箭預測模型最準確的依據。Artemis I 在飛行前用模擬走過所有感測器和資料擷取參數，確認數據足以達成飛行測試目標。 [NASA NTRS：Artemis-1 開發飛行儀器的端到端評估](https://ntrs.nasa.gov/citations/20200003089) 端到端測試的重點是外部介面，用來證明任務系統的各部分能一起運作。 [NASA 系統工程手冊 §5.3](https://www.nasa.gov/reference/5-3-product-verification/)

## 審查門檻

| 審查 | 通過條件 | 不通過時 |
| --- | --- | --- |
| MDR | 完成架構與需求分配。 | 無法進入初步設計。 |
| PDR | 完成初步設計，分析餘裕 ≥ 0 kg。 | 退回。換選項後再送，不另花工期。 |
| CDR | 完成定版，經費付得起硬體。 | 無法開始製造。 |
| FRR | 整合證據對應目前的設計。餘裕 ≥ 0 kg。第一次通聯容量 ≥ 2 單位。 | 退回。修正或重測。 |

FRR 的餘裕以手上最好的證據判定。有熱試車就用試車值，沒有就用分析值。這一章沒有豁免。只靠分析值通過時，審查結論會標明「運載性能尚未經過測試」。

審查名稱和目的依 NPR 7123.1D 附錄 G。 [NPR 7123.1D 附錄 G](https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_7123_001D_&page_name=AppendixG)

## 驗證與任務操作

| 觸發 | 玩家可做什麼 | 結果 |
| --- | --- | --- |

## 實作備註

引擎和畫面這次都沒有改。接上入軌關卡時需要下列支援。多週工作、依任務切換規則、PDR 數值門檻和分段模擬這幾項與[登月計畫的實作備註](lunar-mission.md#實作備註)相同。

1. **預算事件。** 事件改的是總經費，不是期限。工作台要同時顯示目前方案的預估總支出，讓玩家看出缺口。
2. **證據等級。** 運載餘裕有分析值和試車值兩種。做過熱試車後，工作台、FRR 和結算都改用試車值。FRR 結論要區分 `orbitalFrrPass` 和 `orbitalFrrPassAnalysis`。
3. **演練影響容量。** 地面站的 `capacity` 用於沒演練的通聯，`rehearsedCapacity` 用於演練過的通聯。增加第二座地面站後演練要重做。
4. **實驗室時段。** 開局依立方衛星的結算紀錄決定是否出現。`expiresWeek` 之後失效。只能用在 `labSlot.uses` 列出的工作。
5. **履歷輸出。** 結算要寫出 `onTime` 和 `verified` 兩項紀錄，供 `lunar-mission.ts` 的 `records` 讀取。立方衛星目前還沒有輸出「合作驗證紀錄」。
6. **額外目標二擇一。** 承載餘裕要同時滿足有熱試車和試車餘裕 ≥ `marginStretchKg`。診斷資料要 3 單位全數收到。
7. **多人提案。** `orbitalProposals` 列出三個組別可提的返工。接多人模式時要同步更新 `firestore.rules`。
